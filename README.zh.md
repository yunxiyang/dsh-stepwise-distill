# dsh-stepwise-distill

[English](README.md)

让一段很长的 agent 会话保持可用：**过程**不占地方，**结果**留在里面。

两个机制，都发生在步与步之间：

**一、把最新一步的原始材料放回投影。** `Session.deriveMessages()` 是消息列表的唯一来源——请求由它构建，运行时的不变式也拿它与请求比对。只包装这一个方法，两边就一起动，不变式是被满足而不是被绕过。纯函数 `deriveEventMessage` 刻意不动：十一个子系统共用它（含 token 计量），它们必须继续看到日志里原本记下的东西。

**二、每完成一步就写下来。** 一步结束后，额外发一次请求，带上**当前上下文**和一句短指令，只回答刚刚那一步。写法是**那一步的完整记录，不是它的摘要**——写下的文字是 agent 之后唯一还能看到的该步记录，写薄了就等于丢掉它自己的任务史。

没有一样东西被删除。事件日志只追加，`history_read` 可以按 seq 取回任何原文。

## 为什么是这两样

目标不是把账单变小——这个插件是花 token、花时间的，见[代价](#代价)。目标是：一小时之后，agent 在它自己的上下文里仍然找得到当初那个要求。

跨会话统计下来，assistant 自己的输出大致是：

| | 占 assistant 内容的比例 |
|---|---|
| 推理 | 17% |
| 回复正文 | 28% |
| 工具调用参数（补丁、脚本正文） | 55% |

推理的分布很不均匀。某次会话里它**在多数轮里为零，而前四轮共计 143 KB**——那是探索阶段，模型在弄明白任务到底是什么。恰恰是那一段里走错的弯，会被之后每一轮反复重读。

工具调用参数通常是补丁或脚本正文：内容早已落进文件，每轮重发全文买不到任何东西。

## 怎么工作

**1. 把最新一步自己的材料放回投影。**

`Session.deriveMessages()` 是消息列表的唯一来源——请求由它构建，运行时的不变式拿它与请求比对。包装这一个方法让两边一起动，所以不变式是被满足的，而不是被绕过的。

纯函数 `deriveEventMessage` 刻意不动：十一个子系统共用它，包括 token 计量，它们必须继续看到日志里记下的东西。

**2. 写下每一步。**

一步完成后，额外发一次请求，携带**当前上下文**加一句短指令。它只回答刚刚那一步。

答案是**那一步的完整记录，不是它的摘要**。写下的文字是 agent 之后唯一还能看到的该步记录，所以把写薄就是让 agent 丢掉自己的任务史：早先的版本要求「一到三句话」，产出的描述薄到无法据以工作，agent 只好把已经做过的事重新推一遍。长度应当跟着这一步走。

发的是真实上下文而不是摘录，这正是要点：看不到任务的答案只能报告那一步做了什么（「对 Y 跑了 cat」），而拿得到上下文的答案能说出它意味着什么（「在 Y 里确认了 X，Z 需要它」）。

刻意留在外面的是推理本身——把思考也带下去，只会在一个更高的层次上重建这个插件本来要消除的那种翻来覆去。

记录由模型写，永远不由规则合成。判断一步里什么要紧，是对意图的判断，模式做不到这件事。

**3. 扣留已小结的材料。**

一步被写下来之后，它的消息就不再进入投影。下一次请求携带的是更早的那些记录加上最新一步的原始材料。日志里什么都还在。

## 代价

这是一笔交易，不是折扣：它花 token 和实打实的时间，换来一段长会话仍然可读。

**`stepSummary: true`（默认关）每步多发一次请求，而那次请求携带整个当前上下文。** 它不是那一步的摘要：请求内容是摘要用的系统提示词、加上完整的投影上下文、加上一句短指令。所以它的输入开销与你本来就要发的那次请求同一个量级——那一步的输入 token 大约翻倍，外加它写下的那条记录。

**它还会让每一步都变慢。** 小结要在下一次请求构建之前发出，因为「决定那次请求包含什么」正是它存在的全部目的。于是每一步要等两个模型往返而不是一个，在长任务上这是可以感觉到的总时长增加。

`stepSummary: false` 时完全不发额外请求，`debug: false`（默认）在碰到日志文件之前就返回。两种情况都不删除、不改写任何东西：变的只是模型被展示的内容。

节省随时会话变长而增长，这些开销却是固定的，所以盈亏平衡点在长会话那一边。单个短任务上，token 和时间都会比不用这个插件更多。等重放真的成了问题再打开 `stepSummary`，不要提前打开。

## 配置

```yaml
- id: stepwise-distill
  config:
    stepSummary: false        # 每完成一步写一条记录（默认：关）
    turnSummary: false        # 每轮结束写一条补充记录（默认：关）
    debug: false
```

`stepSummary` 默认关，因为它的代价——每步一次额外请求、携带整个当前上下文，以及下一步开始前多一个模型往返。见[代价](#代价)。`turnSummary` 出于同样的理由默认关，只是频率是每轮一次而不是每步一次。

改完**下一步生效，不需要重启**：bundle patch 是普通插入，配置没有被冻结。设置页那张「蒸馏」卡片改的也是同一处。

四个取值都可以在 `Settings > Plugins > 蒸馏` 里改；配置文件里的值作为默认值，卡片改动覆盖它。

启动日志会打出这三个开关的当前值，形如：

```
[stepwise-distill] loaded stepSummary=false turnSummary=false debug=false
```

**装了之后不生效，先看这一行**，再看卡片。这两个开关默认都是关的。

## 安装

```
dsh plugin --profile <name> add dsh-stepwise-distill
```

## 度量

在会话里，`/distill` 报告这个插件扣下了什么：一共有多少步、其中多少步已经小结、以及之后各轮不再携带的原始材料共多少字节。

```
/distill
```

`src/` 下的纯逻辑由 `npm test` 覆盖；那里不需要跑起来的宿主环境。

## 开发

```
npm run build   # src/ -> lib/
npm test        # vitest
npm run check   # lib/ 必须与 src/ 一致
```

`DESIGN.md` 放着完整设计、每条宿主约束对应的代码证据，以及分阶段的计划。

### 宿主包

`history_read` 是通过 `@deepseek-ai/dsh-tools` 的 `defineTool` 注册的，与每一个宿主工具用的是同一个调用。那个包在 DSH 随附的版本上没有发布到 npm，而且它带着一条很深的 peer 依赖链，所以不能声明成普通依赖。它由 DSH 在运行时提供；本地开发时用 `npm run link-host-deps` 从已安装的应用里把它——以及链上的全部——拷出来：

```
npm run link-host-deps          # 从 /Applications/DSH Desktop.app
npm run link-host-deps -- --optional   # DSH 不存在时只警告，不失败
```

`postinstall` 会带 `--optional` 跑它，所以 `npm install` 会自动恢复这些包，并且在没装 DSH Desktop 的机器上仍然成功（只是那里跑不了测试）。拷贝过程直接解析 asar 归档——不用 `asar` 包，不联网。链是从各个包的 manifest 走出来的，不是一张固定清单，所以升级 DSH 不会让它悄悄失效。
